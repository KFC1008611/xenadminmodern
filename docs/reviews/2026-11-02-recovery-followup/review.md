# 断线与重连恢复的同类检查

在 [XVA 重连恢复修复](../2026-11-02-xva-reconnect-recovery/review.md) 后，检查导入/导出取消与清理、VM 复制、模板快速创建、网卡创建、批量电源操作及管理连接恢复。保留此前模板显示与磁盘清理改动，没有操作真实资源池。

## 确认并修复的问题

| 问题与触发条件 | 修复后的行为 |
| --- | --- |
| 导入通过新连接恢复并完成后，窗口仍用旧连接 ID 刷新 VM 和 Task；父页面再次发起旧连接 VM 刷新。 | 使用完成结果携带的当前原池连接，刷新 VM、Task 和模板；去掉重复 VM 刷新，等待页面刷新回调并处理错误。已确认的导入完成不因刷新失败回退。 |
| 导出 Task 已结束，但应用在第一次临时资源清理开始前中断。进度接口将其显示为“清理中”，却因内部已终态而跳过恢复调度。 | 明确尚未尝试清理的记录继续触发恢复，通过当前原池连接清理原 Task/临时检查点。清理完成后移除恢复时的待清理提示，不重新导出或下载。completed、failed、cancelled 三种已知终态均覆盖。 |
| 应用重启后，首次调用直接取消已有任务，取消入口尚未加载 journal。 | 导入与导出取消入口自行加载持久记录；不会误报找不到导入，也不会静默忽略导出取消。 |
| 原池已经通过新连接 ID 重连，用户在下一次恢复轮询前取消导入/导出。取消仍寻找旧连接。 | 核对原操作及提交连接后，按已保存的原池 UUID 找到当前连接，只取消原 Task。取消请求不等同于服务器取消终态。 |
| 旧恢复记录没有原池 UUID，本地连接 ID 又对应其他资源池；取消流程仅比较当前客户端与其自身。 | 拒绝仅凭本地 ID 取消，返回“本地记录缺少原资源池身份”的具体原因，不向当前池发送原 Task 引用。 |

导出的本地恢复提示也改为“本地导出记录已恢复”，不由恢复流程推断应用曾经重启。以上行为已同步到前端规范、桌面工作流和 XVA 规范。

## 复现与回归

新增用例先在修改前运行：[第一组复现](baseline-reproduction-gate.json) 为 2 个文件、33 项，8 项失败，分别对应旧连接刷新、三种导出终态清理、两种直接取消以及两种重连后取消。其余保护通过。另对旧记录缺少池身份的情况单独运行：[身份保护复现](legacy-identity-reproduction-gate.json) 为 14 项中 2 项失败，导入与导出取消均被错误受理；其后补上身份拦截。

最终固定 Node 24.22.0 / npm 11.19.1：

- [专项门禁](focused-test-gate.json)：7 个文件、178 项通过。
- [全量门禁](full-test-gate.json)：200 个文件、2248 项通过，严格集合无漂移，零失败、跳过、todo、warning/stderr。
- Node/Web 类型检查、完整 lint、生产构建和 `git diff --check` 通过。
- [离线界面检查](visual-verification.json)：两种主题、四种桌面尺寸共 8 组通过。导出恢复提示只出现一次且无滚动进度条、不推断应用重启；导入完成后实际 VM、Task 和模板读取均使用替换后的原池连接。页面、面板和弹窗无横向溢出，弹窗保持在视口内，无页面错误。16 张截图与本文件同目录，已人工查看代表性浅色/深色截图。

新增回归核对取消仅发送一次 `task.cancel`，清理恢复仅调用 `task.destroy`；不同资源池及缺少原池 UUID 的取消不发出服务器请求。既有上传、下载、归档校验、取消终态、刷新失败与持久恢复用例一同通过。

## 检查范围与边界

VM 复制在每次观察时按源/目标池 UUID 重新绑定连接；快速创建按池 UUID 与模板 UUID 查找原尝试；网卡创建按池 UUID、VM UUID 和请求 ID 查找原记录。本次检查未复现这些路径永久绑定旧连接 ID 的同类缺陷。批量电源操作在退出或读取失败时保留具体读取故障，不自动重放未取得执行结果的写请求。连接健康检查与重连有代次保护；上述既有回归包含在本次全量门禁内，不能据此断言所有网络故障均已覆盖。

本轮未读取用户那次真实 XVA Task 的最终结果，未取消、清理或重传实际任务。源码修改尚未提交、打包、安装或发布；当前已安装应用不会自动获得修复。
